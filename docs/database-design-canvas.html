Ground rules

Three decisions that shape every table

If we agree on these, the rest of the draft is negotiable detail.

Ledger, not a qty column

On-hand, on-order, and allocated come from stock movements. Available is always computed — never typed in by a user or agent.

Schema per business area

Catalog, inventory, sales, and the rest live in separate Postgres schemas so we do not accidentally join across ownership lines.

Money and qty are integers

Cents and whole units only. No floating-point prices or stock. IDs are UUIDs; SKUs are unique text.

inventory

the hard part · owner-gated

Movements are the source of truth. The snapshot is updated in the same transaction so staff and clients never see a stale “available.”

Why this is not “qty on product”

If on-hand lives on the product row, every PO receive, cancel, and ship races to overwrite the same number. A ledger + snapshot keeps history and prevents oversell under concurrency.

available = on_hand − allocated v1: clients cannot sell against inbound PO qty

v1 boundary

In the first cut vs deliberately later

Keeping the database small is how a solo operator stays sane. These are the same locks as the architecture docs.

In v1

  • One warehouse (location_id = DEFAULT)
  • SKU as the stock identity (no variant aggregate)
  • Available = on-hand − allocated
  • AR: invoices + payments
  • File metadata in Postgres; bytes in object storage

Not in this draft

  • Multi-warehouse transfers / ATP per site
  • Selling against inbound PO quantity
  • General ledger, AP, inventory valuation
  • Separate read replica / CQRS database
  • Product variants as first-class rows

Call agenda

Talking points for the stakeholder review

Walk these in order. Capture decisions in the margins — this page is a draft on purpose.

  1. Does “available” mean on-hand minus allocated?

    Confirm we will not let clients order against stock that is still on a PO. Changing that later is a projection rule, not a rewrite.

  2. When does an invoice appear?

    On order confirm, or when the order ships? Pick one policy for v1 so accounting tables stay simple.

  3. Cart: separate table or draft order?

    Either works. Separate carts are familiar for the shop; draft orders reduce concepts. Decide which language the business prefers.

  4. Customer credit & holds

    Is credit limit enough, or do we need on-hold flags, per-customer pricing, or multiple ship-to addresses in v1?

  5. What must staff see that clients must never see?

    Cost, supplier, other customers’ orders stay off the wholesale schema reads — validate any extra sensitive fields now.

  6. Names & missing tables

    Anything the warehouse team calls differently? Any document (credit memo, RMA, blanket PO) that must exist on day one?
